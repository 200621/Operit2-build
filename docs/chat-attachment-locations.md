# 聊天附件的位置与生命周期

普通文件、粘贴图片在实际导入节点的 `runtime/temp/clean_on_exit` 中保存，保持
`Ephemeral`，不加入 Space 持久化文件同步，不改变现有启动清理机制。

- `AttachmentInfo.nodeId` 记录文件实际所在节点，在文件导入时读取本机已有身份；
  不在消息发送或接收时覆盖为当前执行节点，不新建节点身份。
- 原 `filePath` 保留，供本机预览和直接媒体读取。发送给 AI 的附件标签携带
  `node_id`，并通过 `path` 提供临时目录的 VFS 地址
  `/app/data/temp/clean_on_exit/<文件名>`。
- 文件位于另一节点时，不能通过当前节点的文件 Host 或媒体池读取。远端图片、音频、
  视频回退成带来源信息的附件标签，不因错误的本地媒体读取而中断发送。
- AI 可以直接使用已内嵌内容；确需读取原文件时，先检查节点可达性，再使用
  `switch_core` 在来源节点继续执行。此操作改变聊天执行节点，不是远程文件读取。
- 文件已经清理或来源离线时，需要明确提示重连或重新上传，不搜索其他设备的目录。
- 旧消息和旧附件没有节点信息时保持来源未知，不伪造来源。文本、通知、位置、包信息和
  `@工作区` 等内嵌附件不需要为了读取已附带内容切换节点。

这里同步的是聊天中的位置元数据，不是附件字节。需要长期保存并多端共享的文件，应
实际复制到工作区本体；工作区同步边界见 `workspace-file-sync.md`。
